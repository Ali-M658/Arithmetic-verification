## 5. Zenodo: the deposit and the two ways to mint the DOI

`.zenodo.json` holds:
- the title of the deposit;
- the six creators with names, ORCID iDs and affiliations exactly as on the title pages;
- the description and the keywords;
- `access_right: open`;
- placeholders for the licence and for the three arXiv identifiers (relation `isSupplementTo`).

Zenodo's documentation (fetched 2026-10-10 from help.zenodo.org and developers.zenodo.org) says:
- when a repository has both `.zenodo.json` and `CITATION.cff`, Zenodo uses only `.zenodo.json`;
- the `license` field is required for open access;
- the available licence identifiers are listed by the `/api/licenses` endpoint.

Fill the licence (Section 4, step 2) before either route.

**The deposit archive** is a clean export of the commit, with nothing tracked excluded. Build it at release time from the commit being released:

```
mkdir -p paper/submission/deposit
git archive --format=zip --prefix=hyperbolic-pillow-$(git rev-parse --short HEAD)/ \
    -o paper/submission/deposit/hyperbolic-pillow-$(git rev-parse --short HEAD).zip HEAD
shasum -a 256 paper/submission/deposit/*.zip
```

`paper/submission/deposit/` is git-ignored. Built on 2026-10-10 from commit `b35f0bc` (the commit before the one adding this sentence): `hyperbolic-pillow-b35f0bc.zip`, 21,512,405 bytes, SHA-256 `6e10a9d70e649c51a2e7cae3e3ab807547151e2649f5fc9aef861973ddf1704d`. It holds the 1,354 tracked files of that commit, and its unpacked contents are byte-identical to them (checked file by file with SHA-256); `git archive` produced the same bytes twice. Rebuild it from the commit actually released, after the placeholders are filled. Before any deposit, settle Section 3, item 2 (third-party text in `research/notes/`).

**Way 1: GitHub–Zenodo release.** This needs the repository owner, A. Agadi, because the repository is `github.com/Ali-M658/Arithmetic-verification`.
1. The owner links a GitHub account to Zenodo. Then, from the profile menu, choose "GitHub" and "Sync now", and switch the repository on.
2. Create a GitHub release ("Create release" on the Zenodo GitHub page, or a release in GitHub). Zenodo archives the release with the metadata of `.zenodo.json` and mints the DOI.
3. The DOI exists only once the release is made, so the papers' DOI placeholder can be filled only afterwards. Filling it changes the repository, so make a second release for the final state. Zenodo links the versions (help.zenodo.org, "Manage versions").

**Way 2: manual upload with a reserved DOI.** Any author can do this.
1. Create a new upload on Zenodo. In the DOI field, answer "No" to "Do you already have a DOI for this upload?" and click "Get a DOI now!". The DOI is reserved and can be written into files before upload. Deleting the draft loses the reservation.
2. Fill the DOI into the manuscripts and letters, rebuild, commit and push, then build the zip of that commit with the command above.
3. For a software record Zenodo requires exactly one compressed file. Upload the single zip, choose Resource type "Software", copy the metadata of `.zenodo.json` into the form, and publish.
